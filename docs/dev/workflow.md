# Development rules after 1.0 (proposal)

Status: proposal, 2026-10-04. Applies from the day the first real customer has a real site (the 1.0 launch). Until then the current way stays: one Railway environment `preview` tracking `main`, feature branches, CI on every PR, owner merges by hand. Owner decision: HQ `sb-dev-workflow`.

What changes at 1.0: a merge to `main` must no longer deploy straight to real customers' sites. Everything below follows from that.

## 1. Environments

| Environment | Railway env | Tracks | Purpose |
| --- | --- | --- | --- |
| production | `production` (new) | branch `release` | Real customers. Own Postgres and bucket. `DAILY_SPEND_CAP_EUR` as HQ `liveDailyCap`. |
| staging | `preview` (today's) | `main` | Every merged PR lands here within minutes. Smoke tests, owner clicks through, the eval's `--remote` runs against it. Low spend cap (€3/day). |
| local | docker compose or PGlite | working tree | As today. |

Rules
- Production gets code only through the promote step (§3). Nobody pushes to `release`; CI does.
- Same Docker images and config file in both; only environment variables differ. A feature that must be off in production but on in staging is an env var override of a config key (as `DAILY_SPEND_CAP_EUR` is today), never a code branch.
- Staging data is disposable. It is seeded with the 10 fixtures (`pnpm seed`), never with customer data.
- Cost: a second environment roughly doubles idle cost (about €4 → €8/month at today's size). The €50/month ceiling holds.

## 2. Branches

- `main`: always deployable to staging, always green. Protected: PRs only, CI required, linear history, no force-push.
- `release`: what production runs. Moves only by fast-forward from a `main` commit (§3). Protected the same way.
- Feature branches: `<area>/<topic>` (`editor/photo-crop`, `engine/hero-families`, `ops/backups`), from `main`, one PR each, merged within days, deleted on merge (repository setting "automatically delete head branches"). Agent sessions keep using `claude/<topic>`; the area prefix is for humans.
- Stacked branches only when a spec version forces it (as the template branches did), merged bottom-up on one day, written in the PR description.
- Housekeeping now: 114 remote branches, 80 already merged into `main`. Delete the merged ones at 1.0 (one script run, listed in the PR that does it) and turn on auto-delete.

## 3. Releases

- Semantic versions, tags `v1.2.3`. Patch: fixes. Minor: a feature. Major: a spec change that stops old exports from being re-imported, or a billing change.
- Promote = a GitHub Actions workflow `promote` run by hand: pick a `main` commit (default: head), it fast-forwards `release` to it, tags the version, writes release notes from the merged PR titles since the last tag, and runs the deployed smoke test against production after Railway reports the deploy healthy (~€0.40 in model calls; budget rule applies, so the step is skipped under "spend nothing" and said so in the run summary).
- Cadence: promote when staging has been quiet for a working day and the owner has clicked through what changed. Several small promotions a week beat one big one.
- Hotfix: fix on `main` through a normal PR, then promote at once. Only if `main` carries something not ready for production: branch `hotfix/<topic>` from `release`, PR into `release` (CI runs), then the same commit cherry-picked to `main` in a second PR the same day.
- The running version is visible: `/health` and `/admin` show the tag and short SHA (`RAILWAY_GIT_COMMIT_SHA`), so "which version is live" is one request.
- CHANGELOG.md is generated by the promote step, not edited by hand.

## 4. Data and migrations

- Database migrations run at startup today (web and worker). From 1.0 they must be safe while the previous version is still serving: additive first (new column, new table, backfill), the old column dropped in a later release once nothing reads it ("expand, then contract"). A migration that rewrites or drops data needs the owner's approval in HQ before the promote.
- Spec migrations keep today's rule: version bump, migration, test, and the published sites republished by the worker when the rendering changed.
- Before every promote, CI restores the latest production backup into a throwaway database and runs the pending migrations against it (a `migrate-check` job). This catches a migration that fails on real data before it reaches production.
- Backups: Railway's Postgres backups where the plan has them, plus our own nightly `pg_dump` to the bucket (`backups/<date>.sql.gz`, kept 30 days) and the bucket itself versioned. A restore drill every quarter: restore into staging, open three sites, publish one. Unconfirmed: whether the Hobby plan includes Railway-side backups; checked in the implementation PR.
- Customer files (originals, published releases) live only in the bucket; a site export is the owner's own backup and stays one click away.

## 5. Pull requests

Every PR, human or agent:
- One HQ item (or decision) per PR, linked in the description. Docs-only PRs are exempt.
- Description: what changed and why, how it was checked (the commands run, the numbers), spec or database migration yes/no, screenshots at 1280 and 360 px for anything visual, € spent on model calls.
- Size: about 600 changed lines or less. Bigger work is split or stacked (§2).
- Squash-merge, so `main` has one commit per PR and "merge main into X" commits disappear. The PR title is the commit message: imperative, under 72 characters, area first ("Editor: crop photos in place").
- Required checks (§6) green, and the owner's review. Agent-opened PRs are never self-merged.
- Reviews answer the diff; style nits that a linter could catch become a lint rule instead of a comment.
- Never merged: a PR that skips or deletes a test to pass, prints a secret, or hand-edits rendered output.

## 6. Automation (GitHub Actions)

| Workflow | When | Does |
| --- | --- | --- |
| `ci` (today) | every PR, push to `main` | typecheck, lint, `pnpm test` |
| `ci` additions | every PR | `pnpm eval --offline` (free: golden specs through every check), `pnpm --filter @sb/web build` so a broken editor bundle fails before deploy, migration smoke (`migrate` on an empty Postgres) |
| `promote` (new) | by hand | §3: fast-forward `release`, tag, release notes, migrate-check, deployed smoke test |
| `nightly` (new) | 03:00 | dependency audit (`pnpm audit --prod`), the backup's existence and size checked, stale-branch report (merged branches older than 7 days deleted) |
| `eval` (today) | by hand | real model calls, costs money, budget rule |
| Dependabot | weekly, grouped | one PR for dev dependencies, one for runtime; Playwright and Node pinned to the versions the Dockerfiles use |

Repository settings to turn on at 1.0 (owner, in GitHub settings): branch protection for `main` and `release` as in §2, squash-merge only, auto-delete head branches, secret scanning with push protection, Dependabot alerts.

## 7. Monitoring

Keep it small; nothing here needs a new paid account.
- `/health` already checks the database and storage. A free external monitor (Better Stack, Uptime Kuma on Railway, or cron-job.org) hits production `/health` every 5 minutes and emails the owner on two failures. Creating the account is the owner's step (HQ item).
- Failed jobs, today's spend, the pools and the queue depth are on `/admin`. Add: last 24 h failures by stage, the slowest generation, and the share of generations that hit the spend cap, so the owner sees the pipeline's health without the logs.
- Railway's own alerts (deploy failed, service crashed) go to the owner's email.
- Logs stay in Railway. Every log line that matters already carries the site id and job id; the rule continues: structured `key=value` fields, no secrets, no visitor IPs.
- An error tracker (Sentry's free tier) only if the log search stops being enough; not before.

## 8. Definition of done

A change is done when: the tests that cover it ran green, the thing was looked at in the real app on staging at 1280 and 360 px if it is visible, TASKS.md and the HQ item say what ran and what it measured, the PR is merged to `main`, and (for customer-facing work) promoted to production.

## Order of work at 1.0

1. `production` environment on Railway with its own Postgres and bucket; `release` branch; `promote` workflow; version on `/health` (one PR, the owner creates the environment and sets the variables).
2. Branch protection, squash-only, auto-delete, the merged-branch cleanup.
3. Backups and `migrate-check`.
4. CI additions and `nightly`.
5. External uptime monitor, `/admin` health rows.
