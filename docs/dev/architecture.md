# Architecture notes (phase 1)

Decisions that aren't obvious from the code. Product-level architecture is in `docs/PRODUCT.md`.

## Spec is the only state
Every change to a site produces a new row in `spec_versions` (source: `generate`, `critique`, `edit` (AI chat), `manual` (direct editor), `revert`). Rendered HTML is never stored except as a publish output, and is always re-rendered from a spec version. Undo = revert to an earlier version (a new version is written).

## Two ways to edit
- **Direct editor** (`POST /api/sites/:id/patch`, `/sections`, `/pages`, `/direction`): the dashboard builds RFC 6902 operations; `applyDirectEdit` applies them to a copy, brings design tokens back inside the chosen direction (`enforceDesign`: ranges, contrast) and validates. No model call, no tokens. Forms are generated from the JSON Schemas exported from the zod section schemas, so a new component gets an editor for free. Clicking a section in the preview selects it; double-clicking text edits it in place (matched by exact text within that section's props, so the rendered HTML needs no editor attributes and preview stays byte-identical to published output). Text typed in the editor counts as client-provided for the fact check.
- **AI assistant** (`POST /api/sites/:id/chat`): the only edit path that calls the model. Returns JSON Patch; the same validation plus the fact check apply.

## Facts
Facts live once, in `spec.business`; components render them. The model never writes phone numbers, addresses or hours into copy or links (links use `{action: "call" | "directions" | "email" | "booking"}`). Two code guards back this up:
1. `verifyBriefFacts` drops any brief fact that doesn't literally appear in the client's text.
2. `checkFacts` (after generation, critique and every edit) flags any phone, email, address, hour, price, person's name or other number in the spec that isn't in the client's input (intake + chat + editor text).
Missing facts are `{ "$placeholder": kind }`; `publishBlockers` refuses to publish while any remain.

## Preview equals published
`renderPage` is the one renderer. Preview (`/preview/:id/<page>.html`), publish (a new release at `published/_sites/<slug>/<release>/…`, then the one-line pointer `published/_live/<slug>` switches to it, so a republish never shows half a site; served at `/s/<slug>/`; see `packages/engine/src/published.ts`) and export (zip) all call it with the same inputs. Pages link to each other as `<slug>.html` and to shared assets as `../_shared/<hash>/…`, which resolves correctly at `/s/<slug>/`, on a future subdomain root, and from `file://` in the export (the zip holds `<slug>/` and `_shared/` side by side, plus a root `index.html` redirect).

## Contact forms
The `contact-form` section renders a plain HTML form that posts to the relative `_submit`, i.e. `/s/<slug>/_submit` today and `/_submit` on a future subdomain. Without JavaScript the server answers with a thank-you page; `form.js` submits in place and announces the result in the form's live region. The rendered HTML is the same everywhere (preview = publish = export), so `form.js` decides at run time: in the dashboard preview and in an offline export (file://) it shows a note and sends nothing. The endpoint (`apps/web/src/forms.tsx`) only accepts forms that exist in the site's *published* spec, drops honeypot submissions while answering success, and rate-limits per sender and per site (`limits.formMessages*`). Messages are stored in `form_messages`; the sender is stored only as a keyed hash of the IP (for the 10-minute limit) and cleared after a day, as the generated privacy policy states. Owners read and delete messages at `/sites/<id>/messages`. Email notification to the owner is not wired yet (needs a sending domain). Published pages' CSP allows `form-action 'self'` and `connect-src 'self'` for this.

## Product UI
The landing page at `/` is the only intake: its prompt box posts the description, photos, logo and scope (the scope switch only for those who may make a whole site) to `/api/sites`, signed in or not (the first homepage needs no account; see "Free generation limits"); going to the login from there keeps the typed text in sessionStorage; `/new` redirects to it. It has its own stylesheet, `ui/home.css`. Dashboard, login, editor and messages share one stylesheet, `apps/web/src/ui/app.css`, built on the tokens in `docs/design/ideas.html` §04 (warm canvas, ink, one accent, hairlines, one shadow for floating things, Bricolage Grotesque + Figtree from the render package's subset fonts). It is served with its fonts and icon at `/assets/ui/<content hash>/…` without a session (the login page needs it) and cached for good; the pages carry no inline CSS. The editor bundle builds its DOM with the same classes. Its shell (app bar, panel, canvas) is built once: re-renders replace the bar and panel, while the preview iframe stays in the page (moving an iframe reloads it), and polling reloads it only when the spec version changes. Generated sites never load this stylesheet.

## Accounts and access
Three kinds of visitor (`apps/web/src/access.ts`):
- **Admin**: the product owner, signed in with `ACCESS_PASSWORD` (a signed stateless cookie, `auth.ts`). Sees every site, today's spend, and `/admin`, where the allow-list is managed.
- **Account**: a business owner signed in by magic link (`sb-signin`; `login.tsx`). Email → `login_tokens` row (SHA-256 of a 32-byte random token, `accounts.magicLink.ttlMinutes`, single use by one `update … where used_at is null` statement) → mail (Resend, or the console in development, `packages/platform/src/mail.ts`) → the link opens a page with one "Prijava" button that POSTs the token, so mail scanners that prefetch links don't use it up → a `sessions` row (hash of the cookie's token), cookie `sb_account` httpOnly, SameSite=Lax, Secure when deployed. The answer to a link request is the same whether or not the address has an account. Requests are limited per normalised address and per keyed IP hash. Addresses are normalised (`email.ts`: lower case, `+tags`, Gmail dots and googlemail.com) into `accounts.email_key`, so one inbox is one account; throwaway domains (`disposable-domains.ts`) are refused. An account sees only sites whose `account_id` is its own; any other site id is a 404 (pages, API and preview alike). Allow-listed addresses (`allow_list`, `sb-full-access`) have paid-tier rights before billing: whole sites, publishing, export.
- **Anonymous**: no session. May make one homepage preview and look at it (see "Free generation limits").

Every product page (not published sites, which stay cookie-free) gives the browser a signed device cookie `sb_device`. Every HTML form that changes something carries `_csrf`, an HMAC of that device id; and any unsafe request that the browser marks as cross-site (`Sec-Fetch-Site`) or whose `Origin` names another host is refused (the published sites' `_submit` is exempt). JSON calls from the editor rely on that check plus SameSite cookies.

Refusals from action endpoints are `{ error, code, message }` with a Slovene `message`; `GET /api/sites/:id` carries `access` (`viewer` and `can.*`) so the editor can show what is possible before the owner tries. `spendToday`/`cap` there are the admin's only (null for owners).

## Free generation limits
Every model job a viewer starts (intake, "Ustvari znova", chat edit) goes through `reserveJob` (`apps/web/src/limits.ts`) before `queue.send`. Inside one transaction holding a Postgres advisory lock, so simultaneous requests can't share the last free slot, it checks the global cap, the tier's rules and the tier's pool, then writes an `ai_jobs` row with the job's estimated € (config `tiers.estimatesEur`). The worker logs every call with that row's id, tier and account (`model_calls.ai_job_id/tier/account_id`) and finishes the row when the job ends (`done`, `failed`, or `refused` for junk). A queued row holds its estimate minus what it has logged, so the pools and allowances count real € once calls arrive. Failed and refused jobs don't use up a free generation; a generation that saved a version counts even if a later stage failed.
- **Anonymous** (no account): `tiers.anonymous.homepages` per device (`sb_device`), and anonymous plus free generations per keyed IP hash per 24 h (`perIpGenerationsPerDay`, loose). The site belongs to the device (`sites.device_id`) until someone signs in on that device, or on the one that asked for the link; then the account claims it, and it doesn't use one of the account's free homepages. Unclaimed previews and their files are deleted after `keepDays` by the worker's hourly housekeeping. Anonymous visitors can look at their preview, nothing else.
- **Free account**: `tiers.free.homepages` more and `chatEdits` in total. No whole site, no publish, no export.
- **Paid** (the allow-list before billing): a monthly € allowance of `allowancePercentOfMonthlyPrice` % of `plans.paid.monthlyEur`, plus `firstMonthExtraEur` in the first month. Months run from the allow-list date. Only charged jobs count (photo descriptions don't: direct editing is never limited).
- **Pools**: each tier's share of the daily cap (`tiers.pools`; the admin uses the paid pool), so a flood of previews never blocks paid work. The admin can hold a pool from `/admin` (a hold is an `ai_jobs` row the size of the pool). The worker logs a `[spend]` line per day and warns once per pool and day at `warnAt`.
- **Bot check**: Cloudflare Turnstile on the intake for anonymous visitors (`turnstile.ts`; keys from env). The script loads only once the visitor starts on the form, and siteverify gets no IP. Without keys it is skipped in development and anonymous generation is refused when deployed.
- **Anonymous uploads** (`upload-ticket.ts`): two requests, so nothing large is read before the checks. `POST /api/intake/ticket` takes the text fields only (form token, description, Turnstile token), runs the bot check, the limits (reserving the job) and the junk check, and answers with a signed ticket (job, site id, device, description hash, expiry). home.ts then posts the form with its files to `/api/sites?ticket=…`; a gate checks the ticket and takes its job (once, same device) before any of the body is read, refuses a declared size over `tiers.anonymous.uploads.maxTotalBytes` unread, and cuts an undeclared one off as it streams; then at most `maxPhotos` photos of at most `maxFileBytes`. Any refusal after that gives the job back. Without JavaScript there is no ticket (and no Turnstile), so a preview without an account needs JavaScript.
- Every startup names the optional variables that are missing in one line (`env-check.ts`); none of them stops the server, each only turns its feature off.
- **Junk**: descriptions shorter than `tiers.junk.minDescriptionChars` are refused at once. Before queueing, the web asks the classifier (Haiku); below `minClassifierConfidence` the job is refused and the text stays in the form. If the classifier can't be asked, the pipeline asks it first thing and stops before the brief and before the photos' alt text.
Refusals are Slovene: on the landing page (the form comes back with the text) and as `{ error, code, message, signIn? }` from the API. `GET /api/sites/:id` → `access` carries `can.*`, `allowance` (numbers and a Slovene `text`), `expiresAt` and `signIn`.

## Cost controls
`ModelClient` checks today's spend (sum of `model_calls.cost_eur` since UTC midnight) against `limits.dailyModelSpendCapEur` (or `DAILY_SPEND_CAP_EUR`) before every call and logs every call's tokens and € by stage. Jobs don't auto-retry (`retryLimit: 0`). Static prompt parts are the system blocks, most shared first, each ending in a cache breakpoint: content, critique and edit all start with the section catalogue (~16k tokens), so one generation writes it to the cache once and the later stages read it. Stage prompts (rules) come second. Keep new stages in that order, or they write their own copy of the catalogue.

## Generated images
When the owner gives fewer than `imageGen.pipeline.fillUpTo` photos (per scope: homepage preview or full site), the brief's `imageIdeas` (subjects that never show people, premises, signs or the owner's work) become images from fal.ai (`ImageGenerator`, model and style in config), generated beside the design step. They are stored under `sites/<id>/generated/` and processed like uploads, with `origin: "generated"` on the asset (spec v3). Validation allows them only in hero-split, hero-image, image-text and page-header. The Picture primitive adds an "Ustvarjeno z UI" badge and an alt-text note (EU AI Act Art. 50). Each image is logged in `model_calls` (stage `imageGen`, priced from config), so it counts against the daily cap. Without `FAL_KEY` (or with `pipeline.enabled: false`) nothing is generated; replays use flat stand-ins.

## Photos after generation
The editor's "Fotografije" tab posts files to `POST /api/sites/:id/photos` (optionally `replace=<image id>`). The web process stores the originals, makes the variants and saves one spec version (`addPhotos`); a replace relinks every section and removes the replaced image. Descriptions come from the worker's `alt` job (`describePhotos`, vision model), applied only where the alt is still empty; the site shows "editing" meanwhile so the editor polls. A photo the pages show without a description is a publish blocker.

## Generation timing
Brief and design (classify → brief → design) and the image stage (photo variants, alt text) run side by side; content waits for both. The first saved version is logged as stage `preview` with its time; the editor shows it at once while checks and the critique continue, and a critique result arrives as a new version (dropped if the owner edited in between). The eval reports the median time to that first version.

## Local without Docker
`DATABASE_URL=pglite://…` runs real Postgres in-process (PGlite); pg-boss runs on it through its PGlite adapter, and the web process runs the job handlers itself. `STORAGE_DRIVER=fs` stores objects in a directory. Production uses Postgres + a Railway bucket with the same code.

## Known limits
- Lighthouse runs on the homepage only (per checkpoint); axe and the mobile checks run on every page at 360 and 1280 px.
- Every response carries `X-Robots-Tag: noindex`, including published sites, so Lighthouse SEO on the deployed URL loses the "is crawlable" audit; the eval serves files without the header, like a production host would.
- The export is checked offline (file://) in Chromium by `checkExportOffline` during eval: pages, images, fonts, stylesheet, no network. Other browsers are not verified; Firefox's file:// origin rules may block fonts from the parent `_shared/` folder, in which case system fonts are used.
