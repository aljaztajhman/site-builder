# Architecture notes (phase 1)

Decisions that aren't obvious from the code. Product-level architecture is in `docs/PRODUCT.md`.

## Spec is the only state
Every change to a site produces a new row in `spec_versions` (source: `generate`, `critique`, `edit` (AI chat), `manual` (direct editor), `revert`). Rendered HTML is never stored except as a publish output, and is always re-rendered from a spec version. Undo = revert to an earlier version (a new version is written).

## Two ways to edit
- **Direct editor** (`POST /api/sites/:id/patch`, `/sections`, `/pages`, `/direction`): the dashboard builds RFC 6902 operations; `applyDirectEdit` applies them to a copy, brings design tokens back inside the chosen direction (`enforceDesign`: ranges, contrast) and validates. No model call, no tokens. Forms are generated from the JSON Schemas exported from the zod section schemas, so a new component gets an editor for free. Clicking a section in the preview selects it; double-clicking text edits it in place (matched by exact text within that section's props, so the rendered HTML needs no editor attributes and preview stays byte-identical to published output). Text typed in the editor counts as client-provided for the fact check. Price lists and menus have their own editor (`client/price-editor.ts`, operations in `@sb/spec/price-edit`): groups and items with up/down buttons instead of drag, Slovene price input, "Trenutno ni na voljo"; each item saves whole (so the fact check reads the price with the name it is shown with), the heading fields save on their own paths, and the preview swaps in the section re-rendered by the preview route instead of reloading.
- **AI assistant** (`POST /api/sites/:id/chat`): the only edit path that calls the model. Returns JSON Patch; the same validation plus the fact check apply.

## Facts
Facts live once, in `spec.business`; components render them. The model never writes phone numbers, addresses or hours into copy or links (links use `{action: "call" | "directions" | "email" | "booking"}`). Two code guards back this up:
1. `verifyBriefFacts` drops any brief fact that doesn't literally appear in the client's text.
2. `checkFacts` (after generation, critique and every edit) flags any phone, email, address, hour, price, person's name or other number in the spec that isn't in the client's input (intake + chat + editor text).
   Prices and opening times are paired, not just found (`fact-pairing.ts`, deterministic): a price must be one the client wrote next to a currency (€, EUR, "evrov") for that offering, matched by name with Slovene inflection tolerated (the best-matching mention wins, so "moško striženje 15 €, žensko 28 €" never lets "Moško striženje 28 €" through); an opening or closing time must be one the client gave for every day it is shown for ("pon–pet 8–16", "od ponedeljka do petka od 8.00 do 16.00", "ob sobotah do 12.00", "Saturday 6.30–13.00"). Copy that names nothing the client priced ("cene že od 15 €") still needs one of the client's amounts. A price the client gave without saying what for ("Cene: 15 €, 28 €"), or one the owner typed straight into a price field, counts for any offering. A number the client wrote only as a phone number, year, address or another day's hours never passes as a price or an hour, and a number in copy can't come from a phone number. `verifyBriefFacts` applies the same pairing to the brief. The editor's typed values reach the corpus paired too ("Barvanje: 45 €", "Sobota 9.00–12.00."). A price stated in another language than the offering's name (an English chat message for a Slovene price list) isn't paired, by decision (`sb-english-prices` = strict): the chat edit that adds it fails the fact check (the model is told to use a price placeholder instead), and the owner fills the price in the editor.
Missing facts are `{ "$placeholder": kind }`; `publishBlockers` refuses to publish while any remain.

## Preview equals published
`renderPage` is the one renderer. Preview (`/preview/:id/<page>.html`), publish (a new release at `published/_sites/<slug>/<release>/…`, then the one-line pointer `published/_live/<slug>` switches to it, so a republish never shows half a site; served at `/s/<slug>/`; see `packages/engine/src/published.ts`) and export (zip) all call it with the same inputs. Pages link to each other as `<slug>.html` and to shared assets as `../_shared/<hash>/…`, which resolves correctly at `/s/<slug>/`, on a future subdomain root, and from `file://` in the export (the zip holds `<slug>/` and `_shared/` side by side, plus a root `index.html` redirect).

## Contact forms
The `contact-form` section renders a plain HTML form that posts to the relative `_submit`, i.e. `/s/<slug>/_submit` today and `/_submit` on a future subdomain. Without JavaScript the server answers with a thank-you page; `form.js` submits in place and announces the result in the form's live region. The rendered HTML is the same everywhere (preview = publish = export), so `form.js` decides at run time: in the dashboard preview and in an offline export (file://) it shows a note and sends nothing. The endpoint (`apps/web/src/forms.tsx`) only accepts forms that exist in the site's *published* spec, drops honeypot submissions while answering success, and rate-limits per sender and per site (`limits.formMessages*`). Messages are stored in `form_messages`; the sender is stored only as a keyed hash of the IP (for the 10-minute limit) and cleared after a day, as the generated privacy policy states. Owners read and delete messages at `/sites/<id>/messages`. Each message is also emailed to the site's owner account and nobody else (`apps/web/src/form-email.ts`; a site without an owner account gets none): Slovene, a text body plus an escaped HTML body, Reply-To the visitor's address. The message is stored first; the submit waits at most `formEmail.waitMs` for the send and answers the visitor the same either way; a failed or slow send stays `notify_status = 'pending'` and the web process retries it (`formEmail`), then marks it `failed`, which the messages page shows. A third limit caps one sender across all sites per day. Published pages' CSP allows `form-action 'self'` and `connect-src 'self'` for this.

## Product UI
The landing page at `/` is the only intake: its prompt box posts the description, photos, logo and scope (the scope switch only for those who may make a whole site) to `/api/sites`, signed in or not (the first homepage needs no account; see "Free generation limits"); going to the login from there keeps the typed text in sessionStorage; `/new` redirects to it. It has its own stylesheet, `ui/home.css`. Dashboard, login, editor and messages share one stylesheet, `apps/web/src/ui/app.css`, built on the tokens in `docs/design/ideas.html` §04 (cool blue-white canvas and one deep-teal accent ("Arctic & teal", owner decision sb-ui-palette; `apps/web/test/ui-contrast.test.ts` checks every text pair at 4.5:1 and borders at 3:1), ink, hairlines, one shadow for floating things, Bricolage Grotesque + Figtree from the render package's subset fonts). It is served with its fonts and icon at `/assets/ui/<content hash>/…` without a session (the login page needs it) and cached for good; the pages carry no inline CSS. The editor bundle builds its DOM with the same classes. Its shell (app bar, panel, canvas) is built once: re-renders replace the bar and panel, while the preview iframe stays in the page (moving an iframe reloads it), and polling reloads it only when the spec version changes. Generated sites never load this stylesheet.

## Accounts and access
Three kinds of visitor (`apps/web/src/access.ts`):
- **Admin**: the product owner, signed in with `ACCESS_PASSWORD` (a signed stateless cookie, `auth.ts`). Sees every site, today's spend, and `/admin`, where the allow-list is managed. `/admin/costs` (linked from `/admin`, read-only, `admin-costs.tsx` over `Repo.costs`, `packages/platform/src/costs.ts`) shows model and image spend over the last `?days=` UTC days (30 by default, at most 90): € per run (an `ai_jobs` row: homepage, whole site, chat edit, photo descriptions; by the day it started) with mean, median and p90; € per stage per run (calls without a job are grouped by site and queue job, else alone); spend per day and pool against today's cap and pool shares from config (earlier caps aren't stored); and the top 10 accounts and sites. Only settled `model_calls` rows count; pending reservations (calls in flight) are shown apart, whatever their day. It reads existing data only (the `model_calls(created_at)` index covers the window).
- **Account**: a business owner signed in by magic link (`sb-signin`; `login.tsx`). Email → `login_tokens` row (SHA-256 of a 32-byte random token, `accounts.magicLink.ttlMinutes`, single use by one `update … where used_at is null` statement) → mail (Resend, or the console in development, `packages/platform/src/mail.ts`) → the link opens a page with one "Prijava" button that POSTs the token, so mail scanners that prefetch links don't use it up → a `sessions` row (hash of the cookie's token), cookie `sb_account` httpOnly, SameSite=Lax, Secure when deployed. The answer to a link request is the same whether or not the address has an account. Requests are limited per normalised address and per keyed IP hash. Addresses are normalised (`email.ts`: lower case, `+tags`, Gmail dots and googlemail.com) into `accounts.email_key`, so one inbox is one account; throwaway domains (`disposable-domains.ts`) are refused. An account sees only sites whose `account_id` is its own; any other site id is a 404 (pages, API and preview alike). Allow-listed addresses (`allow_list`, `sb-full-access`) have paid-tier rights before billing: whole sites, publishing, export.
- **Anonymous**: no session. May make one homepage preview and look at it (see "Free generation limits").

Every product page (not published sites, which stay cookie-free) gives the browser a signed device cookie `sb_device`. Every HTML form that changes something carries `_csrf`, an HMAC of that device id; and any unsafe request that the browser marks as cross-site (`Sec-Fetch-Site`) or whose `Origin` names another host is refused (the published sites' `_submit` is exempt). JSON calls from the editor rely on that check plus SameSite cookies.

Refusals from action endpoints are `{ error, code, message }` with a Slovene `message`; `GET /api/sites/:id` carries `access` (`viewer` and `can.*`) so the editor can show what is possible before the owner tries. `spendToday`/`cap` there are the admin's only (null for owners).

## Free generation limits
Every model job a viewer starts (intake, "Ustvari znova", chat edit, photo descriptions) goes through `reserveJob` (`apps/web/src/limits.ts`) before `queue.send`. Inside one transaction holding a Postgres advisory lock, so simultaneous requests can't share the last free slot, it checks the global cap, the tier's rules and the tier's pool, then writes an `ai_jobs` row with the job's estimated € (config `tiers.estimatesEur`). The worker logs every call with that row's id, tier and account (`model_calls.ai_job_id/tier/account_id`) and finishes the row when the job ends (`done`, `failed`, `refused` for junk, or `interrupted` when a restart cut it off). A queued row holds its estimate minus what it has logged, so the pools and allowances count real € once calls arrive. Failed, refused and interrupted jobs don't use up a free generation; a generation that saved a version counts even if a later stage failed. The worker stamps `started_at` when it begins a job; housekeeping ends a row 30 minutes after it started (never while it still waits in the queue), or 30 minutes after it was written when pg-boss has no job for it (an unused upload ticket).
- **Anonymous** (no account): `tiers.anonymous.homepages` per device (`sb_device`), and anonymous plus free generations per keyed IP hash per 24 h (`perIpGenerationsPerDay`, loose). The site belongs to the device (`sites.device_id`) until someone signs in on that device, or on the one that asked for the link; then the account claims it, and it doesn't use one of the account's free homepages. Unclaimed previews and their files are deleted after `keepDays` by the worker's hourly housekeeping. Anonymous visitors can look at their preview, nothing else.
- **Free account**: `tiers.free.homepages` more and `chatEdits` in total. No whole site, no publish, no export.
- **Paid** (the allow-list before billing, with a plan: Osnovni or Plus, `allow_list.plan`): the plan's monthly € allowance `plans.<plan>.ai.allowanceEurPerMonth`, plus `firstMonthExtraEur` in the first month. Months run from the allow-list date. Only charged jobs count (photo descriptions too, since they have an `ai_jobs` row).
- **Photo descriptions** (`alt` job, the vision model, for photos added or replaced in the editor): adding or replacing a photo is direct editing and never limited; describing it is reserved like any model job (`kind: 'alt'`, estimate `estimatesEur.altTextPerPhoto` per photo, `units` = photos), under the tier's pool, a paid account's allowance, and `tiers.altText.photosPerDay` per account in 24 h. Refused, the photo is still saved and `POST /api/sites/:id/photos` answers `altRefused: { code, message }`; the editor shows the Slovene message and the owner writes the description (publishing waits for it).
- **Pools**: each tier's share of the daily cap (`tiers.pools`; the admin uses the paid pool), so a flood of previews never blocks paid work. The admin can hold a pool from `/admin` (a hold is an `ai_jobs` row the size of the pool). The worker logs a `[spend]` line per day and warns once per pool and day at `warnAt`.
- **Bot check**: Cloudflare Turnstile on the intake for anonymous visitors (`turnstile.ts`; keys from env). The script loads only once the visitor starts on the form, and siteverify gets no IP. Without keys it is skipped in development and anonymous generation is refused when deployed.
- **Anonymous uploads** (`upload-ticket.ts`): two requests, so nothing large is read before the checks. `POST /api/intake/ticket` takes the text fields only (form token, description, Turnstile token), runs the bot check, the limits (reserving the job) and the junk check, and answers with a signed ticket (job, site id, device, description hash, expiry). home.ts then posts the form with its files to `/api/sites?ticket=…`; a gate checks the ticket and takes its job (once, same device) before any of the body is read, refuses a declared size over `tiers.anonymous.uploads.maxTotalBytes` unread, and cuts an undeclared one off as it streams; then at most `maxPhotos` photos of at most `maxFileBytes`. Any refusal after that gives the job back. Without JavaScript there is no ticket (and no Turnstile), so a preview without an account needs JavaScript.
- Every startup names the optional variables that are missing in one line (`env-check.ts`); none of them stops the server, each only turns its feature off.
- **Junk**: descriptions shorter than `tiers.junk.minDescriptionChars` are refused at once. Before queueing, the web asks the classifier (Haiku); below `minClassifierConfidence` the job is refused and the text stays in the form. If the classifier can't be asked, the pipeline asks it first thing and stops before the brief and before the photos' alt text.
Refusals are Slovene: on the landing page (the form comes back with the text) and as `{ error, code, message, signIn? }` from the API. `GET /api/sites/:id` → `access` carries `can.*`, `allowance` (numbers and a Slovene `text`), `expiresAt` and `signIn`.

## Cost controls
`ModelClient` (and `ImageGenerator`) reserve every call's estimated cost under `limits.dailyModelSpendCapEur` (or `DAILY_SPEND_CAP_EUR`) before sending it: `Usage.reserveCall` reads today's spend (sum of `model_calls.cost_eur` since UTC midnight, calls in flight included) and writes a pending `model_calls` row at the estimate under one advisory lock, so parallel calls can't both take the last room (estimate: `limits.spendReservation`). After the call the row is settled to its tokens and € by stage, or deleted when nothing was billed. Jobs don't auto-retry (`retryLimit: 0`). Static prompt parts are the system blocks, most shared first, each ending in a cache breakpoint: content, critique and edit all start with the section catalogue (~16k tokens), so one generation writes it to the cache once and the later stages read it. Stage prompts (rules) come second. Keep new stages in that order, or they write their own copy of the catalogue.

## Generated images
When the owner gives fewer than `imageGen.pipeline.fillUpTo` photos (per scope: homepage preview or full site), the brief's `imageIdeas` (subjects that never show people, premises, signs or the owner's work) become images from fal.ai (`ImageGenerator`, model and style in config), generated beside the design step. They are stored under `sites/<id>/generated/` and processed like uploads, with `origin: "generated"` on the asset (spec v3). Validation allows them only in hero-split, hero-image, image-text and page-header. The Picture primitive adds an "Ustvarjeno z UI" badge and an alt-text note (EU AI Act Art. 50). Each image is logged in `model_calls` (stage `imageGen`, priced from config), so it counts against the daily cap. Without `FAL_KEY` (or with `pipeline.enabled: false`) nothing is generated; replays use flat stand-ins.

## Photos after generation
The editor's "Fotografije" tab posts files to `POST /api/sites/:id/photos` (optionally `replace=<image id>`). The web process stores the originals, makes the variants and saves one spec version (`addPhotos`); a replace relinks every section and removes the replaced image. Descriptions come from the worker's `alt` job (`describePhotos`, vision model), applied only where the alt is still empty; the site shows "editing" meanwhile so the editor polls. A photo the pages show without a description is a publish blocker.

## Generation timing
Brief and design (classify → brief → design) and the image stage (photo variants, alt text) run side by side; content waits for both. The first saved version is logged as stage `preview` with its time; the editor shows it at once while checks and the critique continue, and a critique result arrives as a new version (dropped if the owner edited in between). The eval reports the median time to that first version.

Two cost cuts sit behind config `costCuts` (both off; docs/plans/cost-cuts.md items 1 and 7). `secondCritiqueOnlyOnFailures`: after a critique round's patches the site is checked again, and the next round runs only when that check still reports failures; a clean check ends the job with the event "Checks pass after the critique's patches; no further critique round". `contentRetryAsPatch`: a content answer that still fails validation after the code repairs (`repair.ts`) is fixed by an RFC 6902 patch the model writes against that answer as the site places it (homepage first, so the issues' paths point into it), applied and re-validated in code (`content-patch.ts`); a patch that doesn't parse, doesn't apply or leaves issues makes the next attempt the whole-JSON retry. Every attempt counts against `limits.contentRetries`, and a retry sends the latest answer once instead of every earlier one. The job logs each patch retry ("Retried the content answer as patches").

## Local without Docker
**Worker shutdown and recovery** (`apps/worker/src/worker.ts`, config `worker`): on SIGTERM the worker takes no new jobs and lets running ones finish for Railway's draining window (`RAILWAY_DEPLOYMENT_DRAINING_SECONDS` minus `drainReserveSeconds`; `drainSeconds` without the variable; Railway's own default is 0 s, i.e. SIGKILL right away). Jobs still running then are marked: a generation that saved nothing → site `failed` with the "Opravilo je bilo prekinjeno … Poskusite znova." event and its row `interrupted`; one that saved a version → site `ready`, row `done`; a chat edit or photo descriptions → site back to `ready` (an edit also gets a Slovene reply). A worker killed without that stops its jobs' pg-boss heartbeat (`heartbeatSeconds`); pg-boss fails them, and the recovery pass (at start and every minute) marks started rows without a live queue job `interrupted` and busy sites without one `failed`. Jobs still waiting in the queue, or running on another instance during an overlapping deploy, are left alone.

`DATABASE_URL=pglite://…` runs real Postgres in-process (PGlite); pg-boss runs on it through its PGlite adapter, and the web process runs the job handlers itself. `STORAGE_DRIVER=fs` stores objects in a directory. Production uses Postgres + a Railway bucket with the same code.

## Known limits
- Lighthouse runs on the homepage only (per checkpoint); axe and the mobile checks run on every page at 360 and 1280 px.
- Every response carries `X-Robots-Tag: noindex`, including published sites, so Lighthouse SEO on the deployed URL loses the "is crawlable" audit; the eval serves files without the header, like a production host would.
- The export is checked offline (file://) in Chromium by `checkExportOffline` during eval: pages, images, fonts, stylesheet, no network. Other browsers are not verified; Firefox's file:// origin rules may block fonts from the parent `_shared/` folder, in which case system fonts are used.

**Website checker** (`/pregled`, `apps/web/src/checker.tsx`; config `checker`): a public page where anyone types a site's address and gets a report in plain Slovene. Nothing is spent: no model calls. The web refuses an address that isn't public http(s) on 80/443 (it resolves the name), checks the bot check and the per-IP-hash and daily limits, writes a `url_checks` row (migration 14) and queues `check-url`. The worker runs one at a time in its own Chromium (`checkUrl`, `packages/engine/src/check/url-check.ts`):
- Redirects are followed in Node, refusing any hop to a private address.
- The browser aborts every request whose host resolves to a private address, and `*.internal` names never resolve.
- It measures the page at 360×800 with the generator's own page checks, reads cookies set before any interaction and the ZEPT company details in the page text, and runs Lighthouse mobile.

The report page polls with a `Refresh` header and lists what to fix first. Reports are deleted after `checker.keepDays` and IP hashes after a day (housekeeping). `pnpm study <list.csv>` runs the same checks over a list for the small-business study. Per-site rows stay in `eval/runs/study/`; `summary.md` holds aggregates only.

**Product events** (it-analytics, docs/plans/analytics.md Steps 1 and 3; config `analytics`, `events` off by default): Stranko's own funnel and engine telemetry in `product_events` (migration 21; `packages/platform/src/events.ts`). Each step writes one row where it happens, after the step and never in its way (a failed write is logged and ignored): the web process through `tracker` (`apps/web/src/analytics.ts`: landing view, intake submitted or refused with a reason code, limit hit in `reserveJob` and at plan limits, preview opened, upsell shown/clicked, sign-in link asked, sign-in done, preview claimed, direct and chat edits, publish, export), the admin's allow-list (`plan_changed`), the domain provisioning (`domain_connected`), and the worker after each generation job (`apps/worker/src/telemetry.ts`: one `generation` row with stage seconds from the stage log and € from `model_calls`, failed stage, check names, Lighthouse, critique rounds, pictures, retries, cap hits, direction; plus `preview_ready` or `site_generated` for the owner). A device is only `device_key`, an HMAC of the device cookie; no IP, no email, no text the owner typed. The admin's own clicks are skipped. The worker's hourly housekeeping rolls rows older than `keepDays` into `product_events_daily` (per day, kind, tier, plan, source). `/admin/funnel` (steps, conversion and median time to the next step, refusals, limits, previews per tier, upsells) and `/admin/engine` (per-job medians per stage, failures by stage, failed checks, cap hits, the slowest five) read the last 7 or 30 days; `/zasebnost` names it in one sentence while it is on.

**Site statistics** (`apps/web/src/stats.ts`, config `stats`): counts per published site and day, with no cookies (`site_stats`, migration 15).
- **Page views:** counted when the web serves a published `.html` page. Bots, prefetches, 404s and the same visitor reloading the same page within `visitDedupeMinutes` are skipped.
- **Taps:** taps on `tel:` and Google Maps links reach `POST /s/<slug>/_hit` from the always-loaded island `stats.js`, only on the live `/s/` address, at most `tapsPerVisitorPerDay` per visitor.
- **Form messages:** counted when stored.
- **Privacy:** the IP is used in memory only, as a keyed hash; nothing about a visitor is stored.
- **Monthly email:** `sendMonthlyReports` runs hourly in the web process (which holds the mail settings). It sends each published site's owner last month's totals once (`stats_reports` claim plus a Resend idempotency key), in the first `reportWithinDays` days of the month.
